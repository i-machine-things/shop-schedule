# Coding Best Practices & Reminders

> **Style rule:** Notes must be clear and concise — 300 characters or less each. Group by topic, not by date. Whenever a PR review (CodeRabbit or human) catches a mistake, add or amend a note here right away so it isn't repeated.

## Architecture

- **Roku has no web-view component in the public SDK.** This channel can't display `shop-schedule`'s `kiosk.html` directly — it polls a JSON export (`/schedule.json`, same shape as the Python `data` dict) and renders the table natively in SceneGraph instead.
- **`ScheduleScreen.brs`'s scroll loop is a visible reset, not a seamless wrap.** The web kiosk doubles its content and loops the scroll position for a seamless effect; replicating that in SceneGraph (duplicate the content tree, track two scroll positions) is meaningfully more complex for a cosmetic difference. Scroll-to-bottom → pause → snap-to-top → pause → repeat reads fine on a kiosk display and is far simpler to get right.
- **`Rem Hrs`/`#Ops` are per-row, not per-job.** Mirrors `jobboss_db.py`'s SQL: they're the sum/count of everything queued ahead of *that specific operation*, which is why the same job can show different values across its different open-operation rows. Don't "simplify" this to a single per-job value — it would be wrong, not simpler (see the `shop-schedule` PR description's job-30180 worked example for why).
- **No login screen.** Unlike `seerr-roku`, this channel doesn't authenticate against anything — `shop-schedule`'s server has no auth of its own. `SetupScreen` only collects a server URL, once, into the `ScheduleConfig` registry section.
- **Two stacked labels need real vertical separation, not just a few px.** The app header's clock (`clockLabel`) overlapped the report/thru date line (`metaLabel`) above it on real hardware with only a 22px gap between their `translation` y-values -- `font:SmallSystemFont` renders taller than that. Confirmed via screenshot, not guessed; widened the gap to 38px.
- **Only 5 fields are actually shown per job** (job, customer, description, oper, current WC) — an explicit scope decision, not an oversight. An earlier version showed all 11 fields from `schedule.json` on one line and truncated badly on real hardware (Roku's system fonts render much larger than that layout assumed). `schedule.json` itself still carries every field; this screen just doesn't render most of them.

## BrightScript / Roku Patterns

- **Department names/colors must never be hardcoded in this app — they vary per shop.** The original `m.DEPT_COLORS` was a fixed keyword→color table ported from `update_schedule.py`'s `_DEPT_DEFAULTS`, matched via substring on department name. Replaced with `ScheduleTask` fetching `dept_colors.json` (shop-schedule's actual, per-shop-configured colors, editable via `options.html`, same file the web kiosk itself reads) alongside `schedule.json`. `colorsForDept()` now does an exact lowercase-name lookup against that fetched data, matching shop-schedule's own keying, with a neutral gray fallback only for a department not yet in the file at all -- not a hardcoded substitute table.
- **Call it "backlog," not "load."** Shipped the first version as `section.load_weeks`/"wk load"; the actual shop-floor term is backlog. Renamed to match `shop-schedule`'s own correction (`workCenterBacklogText()`, `stickyBacklogLabel`, `.backlog_days`, "wk backlog") after the fact rather than before shipping. `schedule.json`'s field names are shared across both repos -- a rename on one side always means a matching one here.
- **Requested after shipping: "2 wk 3 day," not a decimal week like "2.3 wk."** `schedule.json` sends `backlog_days`/`gap_days` as integers (not fractional weeks) for exactly this -- `fmtWeeksDays()` does `divmod`-style `\`/`Mod` splitting, no rounding needed since the source value is already an exact day count.
- **Don't trust `Str()` or raw `ParseJson()` floats for fixed-decimal display formatting, if a future field ever is a float.** `ParseJson` can hand back `2.2999999999999998` for a server-sent `2.3`, and `Str()`'s own formatting is locale/precision-dependent. For a fixed N-decimal string, scale to an integer, round, then split: `scaled = Int(n * 10 + 0.5)` then `whole = scaled \ 10` / `frac = scaled Mod 10`. (Superseded for backlog/gap display specifically once those became integer days — no longer needed there, but the technique stays valid for any future decimal field.)
- **A fixed x-position for a label next to variable-length text (department/work-center-group names, which vary per shop) will eventually collide.** Confirmed on real hardware via screenshot: the backlog label at a fixed `x=700` overlapped `"Assembly shop - ASSEMBLY"`, one of the *shorter* realistic department/group combinations, not an edge case. Fix: `positionAfter()` measures the preceding label's actual rendered width via `boundingRect()` and positions the next label after it, instead of guessing a fixed offset.
- **A genuinely-missing JSON field must not be treated the same as a present-and-zero one.** Confirmed this exact gap in practice, not just flagged as a theoretical CodeRabbit concern: a `shop-schedule` server running code that predated `backlog_days` made every work center read "open now" during testing -- `section.backlog_days = invalid` (field absent, older server) was defaulting to `0` same as a real reported zero. `workCenterBacklogText()` now returns `""` (shows nothing) when the field is genuinely absent, so a stale/mismatched server reads as silently blank instead of confidently wrong.
- **Standalone `TextEditBox` doesn't work for real text entry on Roku hardware** (same finding as `seerr-roku`) — `SetupScreen` uses a focusable row that opens `KeyboardDialog` on OK instead.
- **A top-level bare assignment statement outside any `sub`/`function` is invalid BrightScript** — `m.COLS = [...]` has to be built inside `init()`, not at file scope above it, even with a comment implying it's "set below." Caught this in `ScheduleScreen.brs` before it ever reached CI.
- **No Node.js available in this dev environment to run `bslint` locally** — written and manually re-reviewed carefully against BrightScript syntax, but CI's lint job is the first real syntax check these files get. Expect to iterate on CI failures for the first PR.
- **A plain `Group` does not clip its children — confirmed on real hardware, not just a guess.** The first version had no `clippingRect` on the scroll viewport; scrolled-up rows rendered on top of/behind the fixed header above instead of disappearing, since nothing told SceneGraph to stop drawing them outside that region. Fix: set `clippingRect="[x, y, w, h]"` (local coordinates) on the viewport `Group` — it's a real, documented field, not something you need a different node type for.
- **Sticky header v2 — timing-based visibility toggling isn't worth it; always-on is more robust.** Two attempts at matching the web kiosk's `position:sticky` exactly (real header + overlay, overlay visibility gated on `scrollY` vs. the section's start position) each produced a different real, hardware-confirmed bug: v1 gated on `scrollY > startY` alone and showed the overlay *and* the real header's remaining portion simultaneously (doubled "PAINTING / PAINTING" text, frozen there); v2 fixed the threshold to `startY + HEADER_HEIGHT` but introduced a "blacks out before being replaced" gap during the handoff. Current version: the overlay is simply always visible once content exists, updated purely from which section index the viewport's top edge is in, no visibility toggling at all. Costs a brief moment of the overlay and the real inline header both showing matching text during a transition — much less objectionable than either previous failure, and there's no timing window left to get wrong.
- **An uncaught error in a tick handler can look identical to the kiosk running out of content, when the real cause is something else entirely.** The scroll freeze reported on real hardware coincided exactly with the sticky-header overlap above, which made it look section-transition-specific -- but a genuinely separate root cause (resetting scroll position to 0 on every 60s refresh, see below) was *also* present at the same time and looked like "the same freeze" until isolated. Don't assume one visible symptom has one cause.
- **Resetting scroll position on every data refresh breaks a kiosk once real content is large enough.** With real production data (~380 jobs), a full scroll-through at this speed takes several minutes -- far longer than the 60s refresh interval. The original `buildContent()` unconditionally reset `scrollY` to 0 on every refresh, so the display could never get more than a minute into the list before being yanked back to the top. Confirmed on real hardware as "restarts instead of showing the whole list" rather than reported as a separate bug at first. Fix: preserve `scrollY` (clamped to the new content's max) across a refresh; only reset to 0 on the very first load or once content shrinks to fit without scrolling.
- **An in-app ECP-keypress "heartbeat" does NOT reset Roku's screensaver/idle timer — confirmed on real hardware, not just suspected.** The approach (periodically `POST http://localhost:8060/keypress/<key>` to simulate a remote press) is a real, documented ECP trick mentioned in Roku community discussion, but empirically: the screensaver still activated *while the channel was actively running and scrolling*, and only a genuine physical remote press woke it. Likely explanation: Roku deliberately doesn't count ECP-synthesized input as "real user presence" for idle-detection, specifically to stop automated/remote tools from defeating the power-saving screensaver. Removed entirely (including the `HeartbeatTask` it required) rather than left in as inert dead weight.
- **The actual working fix: `Video.enableScreenSaverWhilePlaying` (defaults to `false`) blocks Roku's screensaver while any video is playing, at any size** — this is an official, documented SceneGraph field, not a hack. `ghostVideo` in `ScheduleScreen.xml` plays a tiny, off-screen, looping, silent black clip (`media/ghost.mp4`) purely to keep a video "playing" at all times. A real `Video` node works fine directly in a Scene-graph script — unlike `roUrlTransfer`, video playback isn't subject to the MAIN|TASK-thread restriction below, so this didn't need a `Task`. Remember to add any new bundled asset directory (here, `media/`) to **both** `ci.yml` and `release.yml`'s zip packaging commands — easy to forget since the existing ones only listed `manifest components source images`.
- **A `Video` node's `width`/`height` XML attributes only control the on-screen render size, NOT the source clip's encoded resolution.** Confirmed on real hardware: the first ghost-video build used a 16x16px, 5fps clip, and `state` got stuck at `"buffering"` forever (never `"playing"`) regardless of on-canvas placement or render size -- real decoder stall, not a rendering/culling issue. Re-encoding at a more ordinary resolution/framerate/profile (128x128, 24fps, H.264 Constrained Baseline, `-movflags +faststart`) was the actual fix; atypically tiny/low-framerate encodes are plausibly below what Roku's hardware decoder is validated for, even though desktop players handle them fine.
- **Add an unconditional polling print alongside a `state`-change `observeField`, not instead of it, when diagnosing a stuck SceneGraph field on real hardware.** If a field like `Video.state` never changes at all, an observer alone fires zero times and looks identical to "nothing happened" -- a timer that prints the current value regardless of change (confirmed via telnet) is what actually distinguished "stuck at none" (looked like silence) from "stuck at buffering" (same silence from the observer, different real state).
- **A `Video` node's `opacity` field does not blend its decoded frame on real hardware.** `ghostVideo` rendered as a hard-edged, fully-opaque black square at `opacity="0.15"` — confirmed by extracting the actual frames from `ghost.mp4` (solid color, no artifact in the file itself). Video playback uses a separate hardware overlay plane the normal 2D compositor's opacity doesn't reach. Fix: bake the real surrounding background color into the clip's pixels instead of trying to fade it with opacity.
- **A `Video` node shows its own default playback chrome (trick-play/buffering bar) even when unfocused and receiving no key events.** Showed up as a thin colored line across the bottom of `ghostVideo`'s otherwise-solid square — not part of the video file (confirmed via frame extraction). Fix: `EnableUI="false"` on any decorative/ambient `Video` node.
- **A short, tightly-looping `Video` node visibly flashes on real hardware at each loop restart**, even with `state` reported as `"playing"` the whole time (no observable state transition at the flash point — purely a hardware overlay-plane hiccup below the SceneGraph layer). Happened with a 2s clip; mitigated by lengthening to 60s so the restart is far less frequent.
- **Off-canvas placement does NOT block a `Video` node from getting a decode pipeline — that was a misdiagnosis, not a real Roku limitation.** An earlier attempt (`translation="[-100,-100]"`) got zero `state`-change events and was blamed on off-canvas placement; the real cause was the same 16x16px/5fps clip (see above) that stalled identically on-canvas. Retried off-canvas with the fixed clip and it reaches `"playing"` normally — off-canvas is the simplest way to run `ghostVideo` since it sidesteps the opacity, chrome, and loop-flash issues above by just not rendering at all.
- **TODO, deferred:** replace the invisible ghost video with a real **visible, slowly-rotating company logo badge** in the header — same screensaver-blocking mechanism (a genuinely playing `Video` node), but as legitimate on-screen branding instead of a hidden trick. **Real logo to use, confirmed by the user: `Z:\Sales & Marketing\Logos\Logo.PNG`** (310x310 RGBA, a blue/gray gear-shaped "S" emblem — white background, not transparent, so it'll need the background keyed/cropped out before compositing onto the kiosk's dark theme). That network path may not be reachable from every machine/session — worth copying it into the repo (e.g. `images/source/company_logo.png`) the next time this is picked up, rather than re-resolving `Z:\` each time. Otherwise unchanged from before: (1) render a rotation video loop (same `imageio`+ffmpeg approach used for `ghost.mp4` works here), (2) place a modestly-sized `Video` node in the header's empty space between the title and the meta/clock block (roughly x=360–1000 within the y=0–92 header band).
- **While it lasted, that heartbeat *did* teach a real, separately-useful lesson: `roUrlTransfer` is a MAIN|TASK-only component — it cannot be created or used directly in a Scene-graph component's script.** The first implementation called `CreateObject("roUrlTransfer")` straight from `ScheduleScreen.brs` (a `Group`, running on the render thread) and it was fatal: `"roUrlTransfer: creating MAIN|TASK-only component failed on RENDER thread"`, then `"Interface not a member of BrightScript Component"` the instant a method was called on it. **This is not a catchable BrightScript error** — it drops straight into the Micro Debugger and halts every thread, which is why wrapping it in `try`/`catch` never helped despite that being the obvious-looking fix (see "Resilience" below). **Any future `roUrlTransfer`/`roStreamSocket`-type networking call must go in a `Task`, never directly in a `Screen`/`Scene` `.brs`** — this lesson stays valid even though the specific feature it was learned from got removed.
- **Manual scroll (`up`/`down`) pauses auto-scroll rather than fighting it.** `manualScroll()` stops both scroll timers and sets state `"manualPaused"`; a dedicated one-shot timer resumes auto-scroll 10s after the last press, mirroring the web kiosk's own wheel/touch pause-then-resume behavior. A manual press mid-refresh is preserved across the rebuild the same way auto-scroll position is (see above).
- **Column header label x-offsets in `ScheduleScreen.xml` are hand-duplicated from `m.COLS` in the `.brs`, not computed from it.** XML can't reference BrightScript variables at parse time. If `m.COLS` positions/columns ever change, the `columnHeaderRow` labels need the same edit or they'll silently drift out of alignment with the data cells below them.
- **The remote's center/OK button reports as key `"OK"` in `onKeyEvent`, not `"select"`.** Confirmed against `SetupScreen.brs`'s existing (working) `key = "OK"` check before reusing it for the warp menu — easy to get wrong from general Roku knowledge alone since other platforms/docs call this button "select".
- **Confirmed on real hardware: the warp menu's selected-row highlight never applied** when it worked by `row.findNode("bg")` (after `bg.id = "bg"` at creation) inside the loop that set each row's color — every cell stayed the unselected color, no error printed, no crash. Root cause not isolated (the `catch` around it never fired, so it's a logic/lookup issue, not an exception). Switched to keeping a direct `roSGNode` reference returned from `buildWarpMenuRow()` in a BrightScript array instead of re-finding it by id — removes the lookup rather than explains the original failure. STILL UNDER TEST: confirm this fix actually highlights before trusting it.
- **Close any custom modal/overlay `Group` at the top of whatever rebuilds the content underneath it, not just on its own explicit dismiss keys.** The warp menu lists work centers from `m.sectionBounds`, which `buildContent()` replaces wholesale on every 60s refresh; left open across a refresh it would show rows built from a section list that no longer matches `m.sectionBounds`. Simplest fix: `buildContent()` force-closes it first if open, rather than trying to reconcile stale rows against new data.
- **A slide-in/out panel is a plain `Animation` node with a `Vector2DFieldInterpolator` targeting the panel's own `translation` field** (`fieldToInterp="warpMenu.translation"`), started via `m.anim.control = "start"` -- no custom per-frame timer code needed, unlike the main schedule's own scroll loop (which predates this and still uses a timer since it needs continuous looping logic, not a one-shot transition). Two separate `Animation` nodes (open/close, opposite `keyValue` order) stayed clearer than one `Animation` toggled with `reverse`.
- **Hide an animated-out node by observing the close `Animation`'s `state` field going `"stopped"`, not by setting `visible=false` immediately when the close starts.** Setting it immediately would skip the slide-out entirely -- the node would just vanish instead of appearing to leave.
- **First version of the warp menu matched this screen's own per-department section-header styling (colored by `colorsForDept()`) instead of the web kiosk's actual existing sidebar filter (`options.html`: uniform green cells, blue selected-state highlight, left-edge dock).** Caught from a screenshot of the real reference UI, not from re-reading this file's own existing patterns -- when porting/mirroring another surface's UI, check that surface directly rather than assuming internal consistency with this file is the right bar.
- **A fetch failure must not blank the kiosk.** `onScheduleData()` only shows an error banner and leaves the last-rendered schedule in place on failure — matches `update_schedule.py`'s own "keep last displayed schedule" behavior on the Python side for the same reason (an unattended shop-floor display going blank on a transient network blip is worse than showing slightly stale data with a visible warning).

## Resilience

- **An uncaught BrightScript runtime error inside a Scene-graph component's event handler can kill the entire render thread, not just that one callback.** Reported as "the app froze" — a real crash looks identical to a paused animation on a kiosk with no remote interaction, since the last composed frame just stays on screen with nothing left running to update it. **`updateClock()` is the best on-screen signal to tell the two apart**: it ticks every second independent of scrolling, so if the header clock is also stopped, the whole render thread is dead (a real crash); if it's still ticking, it's a recoverable state-machine stall in the scroll logic specifically.
- **A freeze was reported a second time after the first round of `try`/`catch` coverage, at a different section than before — widening `try`/`catch` coverage further did not fix it, because the real cause (see `roUrlTransfer` note above) wasn't catchable at all.** Two rounds of plausible-looking `try`/`catch` fixes were shipped before telnet access was actually set up to check. "A different section each time" was a real and useful clue (scroll position carries forward across refreshes, so time-elapsed explains the varying location) but the specific mechanism still needed an actual stack trace — reasoning from symptoms alone stalled out at "probably somewhere in the tick handlers," which was both true and not specific enough to find this.
- **Not every crash is catchable — `try`/`catch` does not protect against MAIN|TASK-thread component-restriction violations.** These are a distinct failure class from ordinary runtime type errors (`Type Mismatch`, `Invalid use of invalid`, etc.) that `try`/`catch` does handle fine. Don't treat broad `try`/`catch` coverage as proof a crash is now impossible — it narrows *most* failure modes, not all of them.
- **Getting telnet debug console access (`telnet <roku-ip> 8085`) ended the guessing immediately.** Two prior rounds of fixes were built entirely from screenshots and behavioral descriptions. The actual fix, once the real error text was in hand, took minutes. If the device and the dev machine are on the same LAN, this can be connected to and logged programmatically (e.g. a small Python socket script writing to a file in the background) rather than asking the user to run and watch `telnet` manually — worth doing *before* the first guess next time, not after the second one fails.

## CI / GitHub Actions

- **Never interpolate a GitHub Actions expression directly into a `run:` shell block** — pass it through `env:` and reference the env var instead (ref/branch/tag names can contain shell metacharacters).
- A job using `softprops/action-gh-release` needs an explicit `permissions: contents: write` block.

## Easter Eggs

- `components/AppScene.brs::onKeyEvent` — press the remote's "rewind" key 5 times within 2 seconds, from any screen. Shows a small credit dialog. Not mentioned anywhere user-facing.
- Not an easter egg, but similarly undocumented on purpose: pressing "options" on `ScheduleScreen` clears the configured server URL and returns to `SetupScreen`, for re-pointing the kiosk at a different server without a factory reset. Deliberately not advertised in the UI — this runs unattended on a shop floor TV.
